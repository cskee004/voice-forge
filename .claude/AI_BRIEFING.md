## 1. What VoiceForge Is

VoiceForge is a **HACS custom integration for Home Assistant** that transforms the HA voice pipeline into a character-driven AI assistant experience.

It solves a problem that no existing tool solves: Home Assistant's voice pipeline has no concept of character, persona, or personality. The stock Ollama integration is a raw LLM connection with a text field for a system prompt. VoiceForge replaces this with a full character engine — swappable personas, persistent memory, personal messaging to household members, and animated visual presence across home displays.

### What makes it different from everything else

- **SillyTavern** has character cards and memory but cannot connect to HA voice pipelines
- **The Ollama integration** connects to HA voice but has no character system
- **VoiceForge** is the only solution that does both — character fidelity AND native HA voice pipeline integration

Nobody in the HA community has built this. VoiceForge is a genuine gap being filled.

## 2. Product Strategy

### 2.1 Core Value Proposition

VoiceForge makes the home feel alive. Not just automated — inhabited by a presence with personality, memory, and genuine awareness of the people who live there.

The product delivers this through four interlocking systems:

**Character Engine** — YAML-defined character cards that specify persona, speech rules, example dialogues, lore, and memory behavior. Any character, any personality, fully portable and community-shareable.

**Persistent Memory** — Automatic cross-session memory extraction and injection. Characters remember preferences, schedules, and notable events. Users never manage memory — it simply accumulates invisibly in the background.

**Personal Messaging** — Characters leave asynchronous messages for specific household members, delivered through three layers: kiosk display, voice announcement, and parent push notification. A character can leave a note for a child going to school. A parent can request a character deliver a message on their behalf.

**Animated Visual Presence** — Each character has a sprite sheet of emotional states (idle, listening, speaking, alert, pleased, warning) displayed on the kitchen kiosk and the M5Stack CoreS3 SE living room display. Sprites are generated by ComfyUI on the local RTX 3080 — fully local, no cloud.

### 2.2 Target User

**Primary:** Home Assistant power users who want more than automation — they want personality in their home. Comfortable with Docker and HACS installation. Likely to have local LLM infrastructure already or willing to set it up.

**Secondary:** The HA community broadly — VoiceForge ships with four ready-to-use founding characters. A non-technical user can install it and have a fully working character voice assistant without writing a single line of YAML.

**Long-term:** Anyone who discovers VoiceForge through community channels (Reddit r/homeassistant, HA forums, YouTube) and wants the experience without the infrastructure overhead.

### 2.3 Distribution Strategy

VoiceForge ships as a **HACS custom integration** — the standard community distribution channel for HA. This means:

- One-click install for any HA user with HACS
- Automatic update notifications through HACS
- Discoverability through the HACS integration directory
- Community credibility — HACS is where serious HA integrations live

Founding four characters ship bundled with the integration. Community character cards are distributed via GitHub — users fork, author, and submit pull requests. The character card schema is fully documented and designed for community extensibility.

### 2.4 Why Ship Now

The HA voice ecosystem is actively growing. Matter, Wyoming, local STT/TTS, and local LLMs have all matured to the point where a local-only voice assistant is genuinely viable for the first time. VoiceForge enters at exactly the right moment — when the infrastructure is ready but the personality layer doesn't yet exist.

## 4. Architecture Summary

### 4.1 Integration Layer

VoiceForge registers as a **conversation agent** in Home Assistant — the same slot used by the native Ollama integration. It appears in the Assist pipeline configuration and can be selected as the conversation agent for any voice satellite.

VoiceForge does not replace Ollama — it calls Ollama internally. It is a character management and prompt rendering layer that sits between HA and the LLM.

### 4.2 Key Components

| Component | Purpose |
|---|---|
| `conversation.py` | Core ConversationEntity — handles pipeline requests, safety checks, LLM calls |
| `character_manager.py` | Loads, switches, and hot-reloads character cards |
| `template_engine.py` | Renders system prompt from character card + live HA state + memory |
| `memory_manager.py` | Extracts, stores, and injects persistent memory per character |
| `sprite_manager.py` | Manages emotion state machine, fires HA events for display surfaces |
| `comfyui_client.py` | Generates sprite GIFs via ComfyUI REST API on Windows PC |
| `esphome_generator.py` | Generates ESPHome config for M5Stack CoreS3 SE display |

### 4.3 Safety Architecture

VoiceForge has an immutable safety layer that applies to every character regardless of card content. It cannot be disabled, overridden, or circumscribed by any character card or user setting.

Six inviolable rules are injected into every system prompt:
1. Children first — assume a child may be present at any time
2. No harmful content
3. No sexual or romantic content
4. No secret-keeping from parents
5. No medical, legal, or emergency advice — defer to real authorities
6. Emergency override — full character break, plain language, 911 and 988 resources

Rule 6 is implemented as a **pre-LLM classifier** that runs before the LLM sees the message. It cannot be reasoned around. All guardrail triggers are logged to a local safety log visible to HA admin users only.

Each character card defines a `guardrail_response` block — how that character voices a refusal in their own personality. The app triggers the guardrail; the character delivers it in character.

### 4.4 Target Hardware

| Component | Details |
|---|---|
| HA Host | Raspberry Pi 4, 4GB, Docker container |
| LLM + STT + ComfyUI | Windows PC, Ryzen 7 5800X, RTX 3080 |
| LLM | Ollama, `llama3.1:8b`, port 11434 |
| STT | faster-whisper, GPU-accelerated, port 10300 |
| Sprite Generation | ComfyUI, Docker, port 8188 |
| TTS | Piper, Pi 4 |
| Kiosk Display | 27" touchscreen, kitchen wall mount |
| Living Room Display | M5Stack CoreS3 SE, 320x240 IPS, ESPHome |

Repository scaffolding, HACS manifest, config flow, character manager, template engine with live HA state injection and immutable safety layer, conversation agent with pre-LLM emergency classifier, safety guardrail logging, Ollama API integration, TTS post-processing.

**Gate:** All four characters respond distinctly and correctly. Guardrail triggers produce in-character refusals. SHEPHERD adapts to different household members.

### Phase 4 — Sprite & Display System (Day 2 AM)
Emotion state machine, HA event firing on state transitions, ComfyUI client, sprite GIF generation and assembly, sprite serving via HA static files. Generate all 24 sprites (4 characters × 6 emotions). ESPHome config template generation. M5Stack display validation.

**Gate:** ARIA's eye changes state on the kiosk in real time during a conversation. M5Stack displays correct sprite for active emotion.

### Phase 5 — Dashboard Panel (Day 2 PM)
Character library view with animated avatar, message board feed with type badges and time-aware display, memory viewer (collapsed), safety log (admin only), Leave a Message parent override feature, panel registration in HA sidebar.

**Gate:** Full panel renders on kiosk. Message board shows both event and personal messages with correct filtering. Safety log shows guardrail events.

### Phase 6 — Polish & Ship
README, HACS submission requirements, end-to-end test on target hardware, test memory persistence across HA restart, test personal message voice delivery, HACS submission.

**Gate:** Clean install from HACS on fresh HA instance. All four characters functional. M5Stack displaying sprites. Memory persisting across restart.

## 7. Decision Log

Decisions already made by the product owner. Do not relitigate these.

| Decision | Rationale |
|---|---|
| Character cards in YAML, not JSON | Human-readable, community-friendly, HA-native format |
| Safety layer in app, not character cards | Community cards cannot disable safety — architectural guarantee |
| Founding four ship with pre-generated sprites | Zero friction out of the box — install and it works |
| ComfyUI for sprite generation | RTX 3080 already on-site, fully local, no API costs |
| M5Stack compiled per active character (v1) | Dynamic sprite switching requires PSRAM buffering — v2 feature |
| Character editor UI as v1 stretch goal | Core engine first — editor is quality of life, not blocking |
| Memory fully abstracted from user | Users never manage memory — it accumulates invisibly |
| HACS distribution | Standard HA community channel — maximum discoverability |
